# Testing CanopyDB (beginner guide)

This guide walks through **how to think about tests**, then mirrors the suite under `src/test/java`.

Run everything with:

```bash
./gradlew test
```

---

## 1. What is a test?

A test is a small program that:

1. **Sets up** some input (Arrange)
2. **Calls** the code under test (Act)
3. **Checks** the result is what you expected (Assert)

If the check fails, Gradle fails the build — you caught a bug before a user did.

JUnit 5 names that pattern with `@Test` methods and assertions like `assertEquals(expected, actual)`.

---

## 2. How do you know *what* to test?

Ask three questions:

| Question | Prefer testing… | Defer / skip for now… |
| --- | --- | --- |
| Does this have **clear inputs and outputs**? | Pure helpers, SQL builders, pagination math | Code that only paints pixels |
| Would a bug here be **painful or silent**? | Null vs empty cells, filter SQL, offset math | One-line getters |
| Can I test it **without MySQL / a window**? | Models, queries, serializers (with mocks) | Full JavaFX screens, live DB |

**Start at the edges of logic**, not at the UI.

In CanopyDB that means:

```
Great first targets          Harder / later
─────────────────────       ──────────────────────────
CellValue                   ConnectionForm (JavaFX)
ExceptionMessages           NotificationManager animations
ClientStateManager          DatabasePool + real MySQL
TableQuery SQL strings      Full WorkspaceView flows
TableSession pagination     Controllers (need async + UI)
ResultSetValueSerializer    ConnectionManager UI flows
TreeSearch matching
```

Rule of thumb: **if you can describe the behavior in one sentence with “given / when / then”, it’s a good test.**

Examples:

- *Given* a null cell, *when* we copy it, *then* clipboard text is `"NULL"`.
- *Given* offset 0 and 900 rows, *when* we go next, *then* offset becomes 300.
- *Given* a wrapped SQLException, *when* we format for the UI, *then* we show the root message.

---

## 3. What *not* to write (yet)

- Tests that only assert `getX()` returns what the constructor set (low value).
- Tests that need a real MySQL instance (slow, flaky unless you invest in Testcontainers later).
- Screenshot / full-window UI tests (need TestFX and more setup).
- Tests that copy production code line-for-line without asserting behavior.

---

## 4. Unit vs connected vs integration

| Kind | What it means here | Example |
| --- | --- | --- |
| **Unit** | One class, no DB, no UI stage | `CellValueTest`, `TableQueryTest` |
| **Connected (collaboration)** | 2–3 classes together, still no DB | `TableSession` + `TableQuery` + `TableUtilities` |
| **Integration** | Real JDBC / real files / real FX | `ClientStateManagerTest` (temp dir); future Testcontainers MySQL |

Connected tests answer: *“When these modules talk, does the *behavior* stay correct?”*  
They are still fast — they just don’t isolate with mocks as aggressively.

---

## 5. Mocks (faking collaborators)

Sometimes the class you care about needs an object you don’t want to really run — e.g. a JDBC `ResultSet`.

A **mock** is a fake object you script:

> “When `getString(1)` is called, return `"2020-01-01"`. When `wasNull()` is called, return `false`.”

We use **Mockito** for that in `ResultSetValueSerializerTest` (see `build.gradle` — use a recent Mockito, e.g. 5.23+, on Java 25).

You mock **dependencies**, not the class under test.

```
ResultSetValueSerializer  ←── real (under test)
        │
        ▼
    ResultSet             ←── mock (scripted answers)
```

**Fake vs mock:** a *fake* is a hand-written stand-in (e.g. in-memory list). A *mock* is usually generated by a library and scripted per test. Both isolate the unit under test.

## 6. AAA pattern (use this every time)

```java
@Test
void nextPage_advancesOffsetByLimit() {
    // Arrange — build the world
    TableSession session = new TableSession("users", "app");
    session.setTotalRowCount(900);

    // Act — do the one thing
    boolean moved = session.setNextOffset();

    // Assert — check outcomes
    assertTrue(moved);
    assertEquals(300, session.getTableQuery().getOffset());
}
```

Name tests like **behavior**, not like methods:  
`nextPage_advancesOffsetByLimit` beats `testSetNextOffset`.

Mirror production packages so it’s obvious what a file covers.

---

## 9. Mental checklist before writing a new test

1. What **rule** am I protecting? (one sentence)
2. What’s the **smallest input** that shows it?
3. What’s the **observable result**? (return value, SQL string, offset, exception…)
4. Do I need a **real collaborator**, a **fake**, or nothing?
5. Is the test name readable in the Gradle failure report?

If you can answer those, you’re ready to write the test.
